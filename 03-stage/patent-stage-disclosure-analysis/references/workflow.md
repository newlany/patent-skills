# 技术交底分析 Agent 工作流

## 何时使用

在需要对技术交底书进行完整分析、逻辑重构、缺陷审查和发明人补料追问，并且希望把每一步结果都沉淀成独立文档时使用本工作流。

## 默认输出目录

- 如果 `--source` 指向真实文件，默认输出目录为：`<源文件所在目录>/交底分析输出/<源文件主名>`
- 如果 `--source` 只是标签或任务名，默认输出目录为：`<当前工作目录>/交底分析输出/<清洗后的标签>`

## 固定输出文件

工作稿（必有）：
1. `00_交底分析任务索引.md`
2. `01_技术交底分析报告.md`
3. `02_技术交底逻辑重构与缺陷审查报告.md`
4. `03_需要发明人补充说明的问题清单.md`

正式稿（公式/版式敏感交底书必须生成）：
1. `01_技术交底分析报告.docx`
2. `02_技术交底逻辑重构与缺陷审查报告.docx`
3. `03_需要发明人补充说明的问题清单.docx`

## 执行顺序

1. 先创建输出目录和文档骨架。
2. 完整读取交底材料。
   对于包含较多公式的 `docx`，优先用 `$patent-support-docx-math` 的相关读取能力生成保留公式的中间稿，再据此阅读和引用公式。
3. 先写 `01_技术交底分析报告.md`，建立技术背景、技术问题、核心方案和技术逻辑链。
4. 如果下游目标是专利撰写、创造性判断、技术方案重构或申请前把关，在 `01` 完成后先调用 [$patent-stage-prior-art-search](/Users/chrynos/.codex/skills/patent-stage-prior-art-search/SKILL.md) 做首轮查新，明确最近现有技术、拥挤路线和可重构方向。
5. 再写 `02_技术交底逻辑重构与缺陷审查报告.md`，在识别撰写风险、表述问题、支撑不足和回退层级缺失的同时，吸收最近现有技术带来的收窄、保留和淘汰建议。
6. 如果同一项目下已经存在前案分析文档、问题清单、交底问题纪要等材料，并且用户要求比对、去重或沿用其写法，在完成 `03_需要发明人补充说明的问题清单.md` 之前先读取这些材料。把它们作为排重清单和样式参考，只保留本案新增或仍未解决的问题。
7. 最后写 `03_需要发明人补充说明的问题清单.md`，把前两份文档和首轮检索暴露出的缺口转化为可答复的问题。
8. 对于公式较多的交底书，执行 `python3 scripts/export_markdown_bundle.py --output-dir <输出目录>`，生成 `.docx` 正式版。默认正式稿只导出 `01` 至 `03` 三份文档。该脚本已使用数学友好读取格式，前提是 Markdown 工作稿中的公式采用 TeX 语法。
9. 对于公式较多的交底书，导出完成后再用 `$patent-support-docx-math` 检查生成的 `.docx`，确认公式已作为 Word 数学对象输出，而不是意外变成嵌入对象或图片。
10. 每完成一步，都同步更新 `00_交底分析任务索引.md` 的状态；如果中途调用了查新 workflow，也把检索备忘和保存路径记进索引。

## 质量要求

- 所有结论优先基于交底书记载内容。
- 不得自行补造部件、参数、流程、材料、实验结果或技术效果。
- 必须区分 `交底书明确记载`、`推断`、`信息缺失`。
- 需要图文一致性、术语一致性、参数完整性、因果链条完整性检查。
- 如果已经生成了首轮查新结果，`02` 必须区分 `交底本身的缺陷` 与 `最近现有技术导致的重构或收窄建议`，`03` 应把尚未区分开的发明点转化为可追问的问题。
- 如果报告中需要出现公式，不要把公式写成普通字符拼接文本，应在 Markdown 工作稿中使用 TeX 数学语法，例如 `$x_e$` 或 `$$\\sigma_{PN}=(\\sum_{e=1}^N\\sigma_{e,VM}^P)^{1/P}$$`，再导出为 `.docx`。
- 在缺陷审查和问题清单中，不要使用模型内部生成的段落序号定位问题，优先使用步骤编号、章节标题、附图编号和原句片段定位。
- 在问题清单中，先写出有疑问的原文内容或其关键片段，再提出需要发明人补充的问题，语气保持自然、专业、便于答复。
- 如果用户提供了前案问题文档或明确要求参照某份现有文档的格式，优先沿用该文档的编号粒度、段落组织和行文方式；不要强行套用默认大纲。
- 问题清单的语言尽量直接、顺畅，不要为了“像真人”而堆砌夸张、口语化或空泛的修辞。
- 如果只完成部分步骤，也要更新索引文档，让后续接手者能继续推进。
