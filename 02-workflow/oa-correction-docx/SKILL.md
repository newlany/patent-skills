# OA Correction DOCX

## Overview

Use this skill when the user asks to process OA “进行中新” correction matters, especially “补正” tasks that require downloading the official notice and original application file before preparing corrected Word deliverables.

This skill coordinates two layers:

- OA access is handled through the local `opencli oa` plugin.
- DOCX correction is handled with `patent-application-correction-docx`, plus DOCX inspection tools when structure risk is present.
- Replacement-page output is generated by filling the approved content into the user's Word templates. Do not split the corrected full application into filing documents for correction upload.

## Safety Rules

- Never store the OA password in this skill, plugin source, shell profile, or generated notes.
- Use `OA_USER` and `OA_PASS` from the environment. For a one-off command, pass them inline only for that command.
- Keep the downloaded official notice and original DOCX unchanged.
- Edit a copy of the original application file.
- Do not add technical content beyond the original disclosure.
- Besides the notice items, you may repair low-risk formal defects found in the claims or specification when the fix is directly supported by the original file, the drawings, or an internal consistency rule.
- Keep主动检查修改 separate from通知书修改 in the change log.
- If a proposed fix can affect claim scope, technical effect, or embodiment support, stop and ask before editing.
- If the notice can be cured in more than one legally meaningful way, stop and ask before editing.
- Mandatory stop 1: before modifying any DOCX file, provide `补正处理说明.md` or an equivalent correction plan to the user. Include notice items, safe self-check items, proposed edits, and planned OA “补正内容” rows. Wait for user confirmation before editing files.
- Do not upload finished files to OA unless the user explicitly asks for upload.
- Do not trigger OA 转档 unless the user explicitly confirms that the saved OA correction content and final-file upload may be converted.
- Mandatory stop 2: immediately after triggering OA 转档, tell the user that 转档 has been clicked or submitted. Stop there. The user will confirm and complete the official submission manually.

## Workspace Convention

This storage rule is mandatory for every new correction matter. Before downloading any OA file, create a dedicated case folder under the fixed root below. Do not download official notices, original application files, corrected drafts, replacement pages, or OA records into a temporary project folder unless the user explicitly asks for a temporary run.

Store every correction matter under this fixed root:

```text
/Users/chrynos/专利工作区/日常工作/补正处理
```

Create one case folder for each correction matter before downloading official files. At minimum, the visible folder name must include the case volume, case name, and customer name. When OA provides the customer case number and application number, include them too. Use this standard format:

```text
补正-{Z案号}-{案件名称}-{客户名称}-{客户案号}-{申请号}
```

Use OA candidate metadata for `caseVolume`, `caseName`, `customerName`, `customerCaseNo`, and `appNo`. The local `opencli oa correction-candidates` and related correction commands return `customerCaseNo` from OA's basic information field `case_volume_customer`, and return `appNo` from `app_no`.

If a legacy command output lacks `customerCaseNo` or `appNo`, enter the case context through OA and read the Basic Info data with `FilingAction.ashx GetCaseInfo`; `TableRows[0].case_volume_customer` is the customer case number and `TableRows[0].app_no` is the application number. Use `客户案号待补` only when the field is blank in OA, and record that in `补正处理说明.md`.

All downloaded OA source documents must stay inside that case folder. Pass `DOWNLOAD_ROOT` to `correction-download`; the downloaded correction notice and original application DOCX must land under `SOURCE_DIR`. Keep the downloaded files unchanged there, and make all editable copies in `WORK_DIR`.

After this, use these paths throughout the matter:

- `DOWNLOAD_ROOT`: passed to `correction-download`; OpenCLI will put files under `$SOURCE_DIR`.
- `SOURCE_DIR`: unchanged official notice and original application files.
- `WORK_DIR`: corrected combined DOCX, extracted text, and `补正处理说明.md`.
- `REPLACEMENT_DIR`: replacement-page DOCX files for OA upload.
- `CHECKS_DIR`: inspection output, render output, and validation logs when they are useful.
- `OA_DIR`: optional saved OA command output or upload records.

Do not use `./output/oa-corrections` for new matters unless the user explicitly asks for a temporary workspace.

Resolve relative dates first. For “今天” or “当天”, use the current Asia/Shanghai date and state the exact date in the answer.

Check the plugin:

```bash

```



If the user did not identify a case and multiple candidates exist, ask which case volume to process. If exactly one candidate exists, proceed with that case.

Download the notice and original application file:

```bash
opencli oa correction-download Z64119 --from 2026-05-21 --output "$DOWNLOAD_ROOT" -f yaml
```

Verify downloads before editing:

```bash
file "$SOURCE_DIR"/*.pdf "$SOURCE_DIR"/*.docx
for docx in "$SOURCE_DIR"/*.docx; do unzip -t "$docx"; done
```

Use the actual filenames returned by the OpenCLI command. Do not assume they are named `original.docx`.

## Correction Workflow

Create the workspace before any DOCX work. If the helper was not used, at least create the standard subfolders manually:

```bash
mkdir -p "$SOURCE_DIR" "$WORK_DIR" "$REPLACEMENT_DIR" "$CHECKS_DIR" "$OA_DIR"
```

Process the documents in this order:

1. Extract the notice text. For PDF notices, `pdftotext -layout notice.pdf -` is usually enough for first-pass reading.
2. Build a short correction list using the schema from `patent-application-correction-docx`.
3. Run the bundled self-check against the original DOCX.
4. Inspect the original DOCX if it contains formulas, drawings, tables, comments, tracked changes, or unusual numbering.
5. Draft `补正处理说明.md` before editing. It must map every notice item and every safe主动检查 item to the intended edit.
6. Add planned OA correction rows to the same plan: file name, position in file, before-correction text, and after-correction text.
7. Stop and ask the user to confirm the plan. Do not edit files before confirmation.
8. After confirmation, copy the original DOCX into the work folder and edit only the approved items.
9. Record every applied edit in `补正处理说明.md`, keeping notice items and主动检查 items separate.
10. Run the self-check again against the corrected DOCX.
11. Generate replacement-page DOCX files by filling the changed corrected parts into the provided templates.
12. Validate that each replacement-page DOCX opens as a Word file, has the correct page header, and contains only its intended part.

Use `patent-application-correction-docx` for the legal correction rules and replacement-page thinking. This OA skill adds the OA intake path, the replacement-template helper, and a narrow self-check pass for obvious formal defects.

## Self-Check Scope

Run the checker before and after editing:

```bash
python /Users/chrynos/.codex/skills/oa-correction-docx/scripts/review_correction_docx.py original.docx --format text
python /Users/chrynos/.codex/skills/oa-correction-docx/scripts/review_correction_docx.py corrected.docx --format json
```

Check and, when safe, fix these items:

- Claims: duplicate figure marks, standalone punctuation paragraphs, repeated sentence-ending punctuation inside one claim, invalid dependency references, and visible full-width punctuation typos.
- Specification: duplicate or glued figure marks, figure-mark inconsistency introduced by claim correction, obvious punctuation typos, mismatched figure labels, and section-boundary problems.
- Abstract: only fix the same low-risk marker or punctuation problem when it is directly mirrored from the corrected claims or specification.

Do not use this pass to rewrite claims for clarity, add embodiments, broaden terminology, or improve style. Treat those as drafting suggestions unless the user explicitly approves them.

When layout matters, render the DOCX files to PDF or PNG and inspect at least the first page. Confirm that the headers are `权利要求书`, `说明书`, and `说明书摘要`, not a header copied from another document part.

## OA Filing Content

Use this stage only after the corrected DOCX and replacement-page documents are ready.

First run a dry-run plan. Include the correction notice metadata from the official notice:

```bash
opencli oa correction-filing Z64119 \
  --from 2026-05-21 \
  --explanation "$WORK_DIR/补正处理说明.md" \
  --oa-date 2026-03-25 \
  --oa-name 第一次补正通知书 \
  --oa-serial-no 2026032500738440 \
  -f yaml
```

Review `items`, `rowPayloads`, and `headerPayload`. If the inferred rows are not precise enough, pass `--items` with a JSON array containing `fileName`, `position`, `before`, and `after`.

For precise inference, `补正处理说明.md` may include a table under `## OA 补正内容`:

```markdown
| 编号 | 文件名称 | 文件中的位置 | 补正前 | 补正后 |
| --- | --- | --- | --- | --- |
| OA-01 | 权利要求书 | 权利要求10 | ... | ... |
```

After the user confirms the OA correction rows, save the content into OA:

```bash
opencli oa correction-filing Z64119 \
  --from 2026-05-21 \
  --explanation "$WORK_DIR/补正处理说明.md" \
  --oa-date 2026-03-25 \
  --oa-name 第一次补正通知书 \
  --oa-serial-no 2026032500738440 \
  --execute-save \
  --confirm Z64119 \
  -f yaml
```

This corresponds to opening 案件作业, choosing 处理事项“补正” row, clicking 更多, selecting 递交官方, opening the 递交 tab, then adding and saving each 补正内容 row.

After the correction rows are saved, go to the 待转档 tab and upload the corrected final files. Upload only the replacement-page files that actually changed. For a normal correction that changed claims and specification, upload `权利要求书替换页` and `说明书替换页`. If the abstract changed, include `说明书摘要替换页` in the same upload set:

```bash
opencli oa correction-final-upload Z64119 \
  --from 2026-05-21 \
  --final-dir "$REPLACEMENT_DIR" \
  --replace-selected \
  --execute-upload \
  --confirm Z64119 \
  -f yaml
```

This corresponds to clicking 待转档, clicking 上传定稿文件, uploading the corrected DOCX replacement documents, and selecting them as the final files for this filing. `--replace-selected` clears previously selected final files that are not part of this replacement set. If a matching file was already uploaded, use `--reuse-existing` to avoid uploading a duplicate:

```bash
opencli oa correction-final-upload Z64119 \
  --from 2026-05-21 \
  --final-dir "$REPLACEMENT_DIR" \
  --reuse-existing \
  --replace-selected \
  --execute-upload \
  --confirm Z64119 \
  -f yaml
```

Only after the user separately confirms transfer and the final files have been selected, trigger 转档:

```bash
opencli oa correction-filing Z64119 \
  --from 2026-05-21 \
  --explanation "$WORK_DIR/补正处理说明.md" \
  --execute-convert \
  --confirm Z64119 \
  -f yaml
```

After this command succeeds, stop and tell the user: “已点击转档，后续请你在 OA 中确认并自行递交。” Do not continue to any official submission step.
